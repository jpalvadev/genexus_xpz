After — page passes through a tiny interface

Grid table module

<MasterTable fetch columns labels=new-route />

pagination state · sorting mapping · debounce · filter reset · react-query key · loading — implementation, invisible to the caller

Callers pass a fetcher and a column set; the react-query + gridify + sort-mapping dance becomes internal to the module.

  • locality: wiring bugs concentrate in one module
  • interface shrinks: 9 facts → fetcher + columns
  • tests move from hook mocks to composition
  • leverage: one interface, seven call sites

Problem. Gridify filter grammar (and the magic PageSize=1000 in getAll) leaks into UI-adjacent code; every consumer must learn the wire language, and a query that Gridify rejects is a UI bug.

Solution. Fold query-language construction into a deep Lookup module: interface takes term + page size, wire syntax is implementation. (C1 absorbs this naturally.)

  • seam discipline: wire syntax stops leaking
  • lookup tests stop hand-building filter strings

Top recommendation

Start with Candidate 1 — collapse the five master-catalog clones into one Master record module. The seams are already proven: crudMasterHandlers in MSW, four byte-identical services on the backend, and the glossary names all five (Observer, Plant, Sector, Contractor Company, Combo Option) as the same shape — "an Id and a Name." The module family is the repo's hottest spot, and the deepening is mechanical: factories for the four shapes (service, table page, form, action cell), then five configs. Candidate 3's shims fold in as a freebie, and Candidate 2 is the identical move on the backend with no interface change at all — a natural second bite if the frontend lands cleanly.
